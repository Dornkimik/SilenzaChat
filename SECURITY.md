# Private chat security model

Private messages and attachments are encrypted and authenticated by the browser. The server does not receive plaintext messages, captions, attachment contents or filenames, private identity keys or attachment keys through the supported client. Public rooms remain plaintext. This application integration has not undergone an independent cryptographic audit.

## Construction and key lifecycle

- The browser uses the pinned `tweetnacl@1.0.3` implementation, served from the same origin without a CDN. [TweetNaCl documentation and audit information](https://github.com/dchest/tweetnacl-js) describe the underlying NaCl constructions. The library audit is not an audit of this application.
- An anonymous session gets an X25519 identity key pair, stored in IndexedDB. Creation is atomic across tabs. Only the public key is registered on the server; the server refuses replacement keys for an existing session. Losing the local key requires a new anonymous session.
- Private envelopes use NaCl `box` (X25519–XSalsa20–Poly1305) with fresh cryptographically random 24-byte nonces. Session IDs, sender, recipient, client message ID, reply reference, text and attachment descriptor are inside the authenticated ciphertext. Clients check these against the transport envelope after decryption. This prevents silently moving a ciphertext to another sender, conversation, reply or message ID. Invalid or unauthenticated content is never rendered as a message. Before encryption, private and room message plaintexts are padded with trailing JSON whitespace to a multiple of 512 bytes, so a ciphertext reveals only a coarse length class rather than the exact message length.
- Each attachment gets a fresh independent 32-byte key and 24-byte nonce for NaCl `secretbox`. Its key, nonce, kind, allow-listed MIME type, size, dimensions (images and videos) and, for generic files only, a sanitized name travel inside the private message. Only a random attachment ID and expiry are exposed outside. Before encryption the plaintext is zero-padded to a Padmé size class (at most about 6% larger), so the server learns only an approximate size. No server-side plaintext thumbnails are created.
- Media metadata is removed locally without canvas or any pixel/sample re-encoding. The format is detected from the bytes, never the filename or browser-reported type. JPEG keeps only decoding segments plus an Orientation-only EXIF record and drops everything after the end-of-image marker; PNG/APNG, WebP, WAV and GIF are rebuilt from allow-lists of rendering chunks/blocks; MP4/MOV/M4A `udta`, `meta`, `uuid` and `free` boxes are overwritten in place as zero-filled `free` boxes, handler names and creation/modification times are zeroed; WebM titles, dates, muxer/writer names, segment UIDs, track names, tags, chapters and embedded attachments are overwritten with Void elements; MP3 ID3/APE tags are cut. Timed metadata tracks inside a video's media data are not rewritten. Other files (including HEIC/AVIF) are sent unchanged, as downloads only, and the composer states that their internal metadata is not removed.
- After authentication, an attachment is shown only if its decrypted bytes match the declared allow-listed format; SVG, HTML and server-provided MIME types are never rendered. Images over 64 megapixels (read from the header) are rejected before decoding. Videos, audio and files are downloaded only when the recipient asks. Generic files are saved through an `application/octet-stream` blob with a download name and are never opened as a page in the site's origin. Blob URLs are revoked on conversation changes, message removal and expiry. Decrypted message state and drafts remain in browser memory; they are not saved to server storage or browser persistent message storage.

This uses established authenticated-encryption constructions, not Signal's messaging protocol. **There is no double ratchet, forward secrecy or post-compromise recovery.** A stolen browser identity private key can expose previously captured ciphertext for that identity. Clearing site data loses access; server restart creates a new session identity. There is no multi-device sync or key backup. Explicit sign-out clears current and obsolete local private keys and peer pins in both current and legacy storage. Other open tabs invalidate their encryption clients and leave the chat. Revocation markers retain session IDs without keys to prevent old tabs or migration from recreating signed-out identities. Unused keys may remain until explicit sign-out or site-data clearing; browser storage cleanup is not guaranteed forensic erasure.

The client selects authentication by conversation type, not by the presence of ciphertext. Private and temporary-room history, live messages, and edits with missing, malformed, or unauthenticated envelopes remain locked. Mixed public/private/group routing metadata is rejected. Public plaintext messages cannot be routed into an encrypted conversation.

## Identity verification

First contact pins the peer's public key locally (trust on first use). A different key for the same anonymous session blocks private communication; it is not accepted silently. Both participants can compare the same 256-bit verification code through another trusted channel. The code is a domain-separated SHA-512 hash truncated to 256 bits over the sorted session IDs and public keys. Verification is stored locally for that peer and key.

Each identity also has an Ed25519 signing key, derived in the browser from the encryption secret key with a domain-separated SHA-512 hash, so no additional secret is stored. Its public half is published with the encryption key and pinned with it on first contact; a different signing key for the same session is rejected. When both participants have signing keys, the verification code covers the signing keys too (a separate `v2` domain). A peer pinned before signing keys existed gets its signing key pinned on first sight and is marked unverified again, so the new code must be compared again.

An initial server-substituted key cannot be detected by trust on first use alone. Compare the code out of band to authenticate the contact. Encryption does not establish a person's real-world identity from their random alias.

## Message time and ordering

New private and room envelopes include the sender's clock (`sentAt`) inside the authenticated ciphertext. The client shows a warning beside a message when it differs from the server timestamp by more than five minutes, which can indicate a delayed or backdating relay (or simply a wrong device clock). Edits keep the original sender time; older messages without one remain valid. Display order, aliases and admin badges are still server metadata, and a malicious server can still withhold messages. In rooms, each member receives a separately encrypted envelope, so a sender can give different members different text; there is no cross-member consistency check.

## Storage, delivery and deletion

The server holds only the latest 100 encrypted envelopes per private conversation. Attachments use bounded process memory (128 MB total, 20 MB per uploader and 24 MB per client address, including reservations for simultaneous uploads) and are never written to disk by the application. Uploads are limited to 4 MiB plus the 16-byte authentication tag. The server cannot prove arbitrary client-supplied bytes are encrypted; the supported browser client encrypts before sending, and the API rejects plaintext message fields.

An attachment can be claimed once, by its uploader, for the intended recipient. Both participants must have registered encryption identities. Downloads require a session cookie and are restricted to the uploader and, after publication, the recipient. No public attachment links exist. Responses use `Cache-Control: no-store`.

Unpublished uploads expire after 10 minutes. Published attachments expire 24 hours after upload, or sooner with `ATTACHMENT_TTL_SECONDS`. Expired downloads are immediately denied; a sweep frees expired memory at least once per minute. Removal, history eviction, a participant's ban/session expiry and server restart also delete attachments. Offline recipients can retrieve them while that session/history remains available. Downloaded or captured copies cannot be remotely erased. A malicious server could retain ciphertext despite expiry; encryption is the confidentiality protection.

Private reply quotes are resolved from the locally decrypted original message instead of duplicating its text into another persistent ciphertext. Removed or evicted originals are shown as unavailable. The server sees reply relationships, but not quoted contents. Admins cannot decrypt other users' private content and cannot inspect attachments for moderation. Admin message removal still works by message ID.

## Temporary encrypted rooms

User-created rooms reuse the existing NaCl box construction and browser identity keys for encrypted text, attachments, captions, replies, and mentions. The sender creates a separate authenticated envelope for each member, including itself; the server returns only the requesting member’s envelope. Ciphertexts bind a `group` domain marker, room ID, membership version, message ID, sender ID, recipient ID, reply ID, and attachment descriptor. Recipient keys and historical sender keys are pinned through the same IndexedDB trust-on-first-use checks as private chats. A member’s verification code can be compared independently from the room details panel. There is no shared long-lived group secret and no plaintext fallback.

Each group attachment uses the existing independent random secretbox key and nonce, shared only inside the per-member encrypted envelopes. Uploads are bound to the uploader, room, and membership version. Membership is checked both before and after streaming an upload, and again when claiming it in a message. Downloads require both membership in the original recipient set and continued membership since that message; the uploader has no bypass after leaving or being kicked. New members and rejoining members cannot download earlier attachments, except those of messages shared with them through history sharing. Group uploads cannot be claimed in private chats or other rooms. Attachments share the existing global/per-uploader quotas and expiry, and are removed on message deletion, history eviction, room deletion/expiry, or uploader session removal. Already downloaded copies cannot be revoked.

The server enforces membership for state, history, sends, and removals. No room admits people on their own: joining requires an invitation from the owner or a moderator, an invite link, or a join request that the owner or a moderator approves. Join requests are only accepted for discoverable rooms; hidden rooms are omitted from other users’ directories and cannot be requested. Pending requests are capped per room and per session, are dropped when the requester is banned or their session ends, and are re-checked against bans, locks and the member limit on approval. Invite links are random 144-bit tokens carried in the URL fragment (which browsers do not send to the server in requests), expire after at most 24 hours, can be limited to a number of uses, and can be revoked; anyone holding an active link can join, so they should be shared like a password. Banned sessions cannot use links, and locked or full rooms reject every new join. Every newly accepted send must address exactly the current roster at its current membership version; concurrent joins, departures, or removals invalidate stale submissions. Members joining or rejoining receive only subsequent messages, unless the room shares history (below). Kicked sessions may come back through a new request, invitation or link; banned sessions cannot rejoin until unbanned. Bans, mutes, slow mode, and staff-only posting are enforced by the server per session, so a person can evade them by starting a new guest session. The server cannot erase already delivered ciphertext or plaintext. The same static-key, no-forward-secrecy, malicious-client/server, and first-contact trust limitations described above apply; this is not an audited group messaging protocol. A malicious server can misrepresent membership, and a malicious participant can share what it receives.

### Room history sharing

The owner can let later members read recent history. The setting is off by default and can be changed at any time, but it applies per message: the server records on each message whether sharing was on when it was sent and rejects sends whose flag does not match, and the flag is also bound inside every encrypted envelope. Messages sent while sharing was off are never shared, even if it is turned on later; turning it off stops new messages from being shared but keeps earlier shareable ones shareable. The room header and composer show when sharing is on.

A shareable message carries the author's Ed25519 signature over a domain-separated record of the room, message ID, author, edit version, text, reply, attachment descriptor, and sender time. Original recipients check that signature when they decrypt, so a member never passes on a message that later members would reject. When someone joins, an existing member's browser decrypts the shareable messages it can read and re-encrypts each one, with the signature, in a separate box addressed to the newcomer; the server stores these copies next to the message and only accepts them from members who can read the message, for current members who cannot. The newcomer opens the box with the sharer's key and verifies the signature with the author's pinned signing key, so the member who shares cannot change a message or its author. The sharer can still withhold messages, and anyone who can read history can already copy it, as before.

Shared copies are dropped when the recipient leaves, when the message is edited (members then share the edited version), deleted, evicted or expires. They count toward the room's 4 MiB and the global storage limits, but not toward the original sender's per-client quota. Sharing needs a member who can read those messages to be online; until then the newcomer sees only new messages. The server learns which members received shared history and from whom.

Room names, descriptions, rules, access policy, room settings, roles, mutes, bans, invite links, membership, sender public keys, message counts, timing, and ciphertext lengths are unencrypted metadata. Only the current owner and moderators receive per-member counters, the ban list, and invite links from the API. Counters track accepted messages during the current membership; deletion does not decrement them and duplicate retries do not increment them. They describe participation, not message contents or quality. Other participants can infer activity from messages they receive.

Room state is memory-only. Rooms expire after the owner-chosen period (1, 6, or 24 hours) without messaging or membership/management activity, on deletion, when empty, or on server restart. With disappearing messages enabled, the server deletes stored ciphertext once it reaches the chosen age (checked at least once a minute) and tells clients to remove it; it cannot erase copies already delivered or saved. Session ban/expiry removes membership and transfers ownership to a moderator if there is one, otherwise to the earliest remaining member, or deletes an empty room. Limits are 20 members per room, 200 rooms total, three owned rooms and 20 memberships per session, six owned rooms per client address, 100 messages / 4 MiB of ciphertext per room, 6 MiB of room history sent from one client address, and 64 MiB of total room-history storage. Client-address keys used for this accounting stay server-side and are never included in room state or messages. Group sends share the existing per-session message rate limit. Requests accept at most 512,000 bytes of encrypted envelopes and reject plaintext fields. Owners can remove messages and manage membership without a site-admin role. Owners can appoint moderators, who can approve or decline join requests, invite, create and revoke invite links, mute, kick, ban, unban, and remove messages, but only for regular members; moderators cannot change settings, appoint others, transfer ownership, or delete the room. Authenticated site admins can list metadata for all temporary rooms, including hidden rooms, and edit their name, description, and rules or delete them. Only the owner can change access or invite members through the owner endpoints; the admin moderation endpoint rejects access changes, including when the administrator owns the room. These moderation endpoints do not return membership keys, ciphertext, or history and do not change ownership or membership. Admin access alone does not authorize room history or attachment access. The server still controls the delivered code and roster; this is an application authorization boundary, not an authenticated membership protocol against a malicious server.

## Trust boundaries

- The server still knows participants, aliases, public keys, IP addresses during connections, message timing, reply relationships, attachment IDs and ciphertext sizes (padded to 512-byte classes for messages and Padmé classes for attachments). This does not provide metadata anonymity.
- HTTPS is required outside localhost. Keys require available IndexedDB. Failures disable private messaging; there is no plaintext fallback.
- Browser-side encryption cannot protect against compromised devices, malicious extensions, same-origin script injection, or a malicious deployment serving modified JavaScript that steals plaintext/keys. Trust in the delivered client is required. The CSP permits same-origin scripts only, with no inline/eval or external CDN scripts.
- A recipient can save or share received content. Expiry is a retention policy, not protection from screenshots or copying.
- Message IDs are deduplicated within the retained history. The protocol does not provide durable replay protection, ordering guarantees, or an authenticated server clock. A malicious server can suppress messages or replay an old valid message after it leaves recent history.

Tests cover ciphertext-only API delivery, authentication failures, metadata binding, key pinning, matching verification codes, local key loss, cross-session download isolation, ownership, expiry and quotas. These checks are not a substitute for an independent security review when stronger messaging guarantees are required.

Message edits require the original sender and retain the message ID, timestamp, reply target, and attachment. The server validates monotonically increasing edit versions; encrypted content authenticates that version. Group edits target only current members whose original membership could access the message, never newly joined or rejoined members, and reject changes to the membership roster during encryption. Edits replace stored content without keeping an edit history; previously delivered copies cannot be revoked.

## Accounts and authorization

Accounts store a unique, case-insensitive username, random account ID, server-owned role, random 128-bit salt and a 64-byte scrypt hash (N=32768, r=8, p=3). These parameters follow [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt). Passwords are never stored in plaintext. Hash work is asynchronous and capped at four concurrent operations; login and registration share address, address/username and service-wide throttles. Usernames are limited to ASCII letters, numbers and underscores. Passwords accept 15-128 characters, including spaces, without truncation. Unknown users still incur password hashing; incorrect login errors are generic.

Roles are read from account records on every privileged request. Public registration cannot assign a role. Initial admin creation requires both bootstrap environment values and an empty account store. Cookies are HttpOnly and SameSite=Strict, rotate on authentication, and use Secure for HTTPS origins (or SECURE_COOKIES=true). Mutations require the configured origin. Logout invalidates the session, ends its streams, removes group membership and attachments. Account records survive restarts; browser sessions expire after 24 hours offline or a server restart, so users log in again. Each new session has an independent encryption identity. Account bans survive cookie resets; creating a different account remains possible.

Use HTTPS and durable, access-controlled storage. The JSON account store supports one server process, not multiple concurrent writers. There is no email recovery, password reset UI, cross-device message archive or MFA. Deployment-level connection limits are still needed against distributed abuse.

## Abuse controls and identity separation

Guest creation is limited to 30 per client address and 500 service-wide per ten minutes. Existing sessions remain usable when creation is throttled. At most 4,000 guests share the 5,000-session total, reserving capacity for accounts. One client address may hold at most 30 concurrent sessions (guests and accounts), so a single address cannot accumulate the shared capacity over time. Sessions that never open the chat event stream expire after ten minutes instead of 24 hours. Accounts allow ten concurrent sessions. Event streams allow six per session, 30 per client address, and 2,000 service-wide. These controls bound application resources; distributed abuse still requires edge protection.

Authentication allows 100 attempts per client address, ten per client-address/username pair, and 2,000 service-wide per ten minutes. Registration is additionally limited to five attempts per client address per hour. A username alone no longer causes a lockout shared across unrelated addresses. Address identifiers are hashed with a random process-local HMAC secret. Throttle counters are memory-only, expire, and occupy at most 50,000 entries.

Banning a session also blocks new guest sessions and registrations from its client address for 24 hours, unless another person (including the acting admin) is currently using that address, to avoid locking out shared networks. This block is memory-only, keyed by the process-local HMAC, never written to disk, and lifted by unbanning. Existing accounts on that address can still sign in.

Forwarding headers are ignored by default. Configure `TRUSTED_PROXY_ADDRESSES` with an explicit comma-separated IP/CIDR allowlist for the actual ingress peers and trusted intermediaries. Starting at the socket peer, the server walks `X-Forwarded-For` right to left and stops at the nearest untrusted address. A trusted peer without a valid chain is rejected instead of pooling visitors under its address. The ingress must append/sanitize this header and prevent untrusted direct origin traffic. Do not use a trust-all network. Railway/Cloudflare source networks and header handling must be checked at deployment; branding and arbitrary headers do not establish trust. On Railway, set `TRUSTED_PROXY_ADDRESSES=100.64.0.0/10` and `CLIENT_IP_HEADER=X-Real-IP`: Railway's edge strips client-supplied forwarding headers and sets `X-Real-IP` to the visitor (Cloudflare's `CF-Connecting-IP` when proxied), while its `X-Forwarded-For` ends at the Cloudflare edge. `CLIENT_IP_HEADER` is read only from trusted peers and replaces `X-Forwarded-For` parsing. IPv6 visitors are grouped by /64 prefix, because one subscriber normally controls a whole /64. On hosts that append to `X-Forwarded-For` behind Cloudflare, set `TRUSTED_PROXY_PRESET=cloudflare` in addition to the host ingress network so visitors are not pooled under shared Cloudflare edge addresses; the preset adds Cloudflare's published ranges. On Railway or with `NODE_ENV=production`, startup warns when no trusted proxy is configured. `LOG_CLIENT_ADDRESS_ONCE=true` logs the socket and forwarding addresses of a single request to help identify the ingress network; turn it off afterwards.

Signing a guest into an account ends the guest session and creates a new public session ID and encryption identity. This removes the guest's private history, attachments and temporary-room memberships, and invalidates its cookie and streams. Previous public posts retain their guest sender ID and alias. Reauthentication within the same signed-in account rotates its cookie while preserving its identity. Timing and content can still correlate identities.

Private history is capped at 64 MiB of serialized data globally, 4 MiB per participant, 4 MiB of messages sent from one client address, and 50 conversations per participant, in addition to 100 messages per conversation. Edits must fit the same budgets and are rejected without changing stored messages if they do not. Empty histories release their conversation allocation. Quotas count serialized data rather than the exact JavaScript heap overhead. Private histories expire after 24 hours without a send, edit or deletion, including while peers remain online. Bans, logout, guest-to-account transitions and session expiry all use the same cleanup. An independent sweep removes orphaned histories and their images.

With an HTTPS `ORIGIN`, application responses include `Strict-Transport-Security: max-age=31536000`. Subdomains and preload are not opted in automatically. Confirm the edge forwards this header and redirects HTTP after deployment. Event streams use `Cache-Control: no-store`. All responses also send `Permissions-Policy` (camera, microphone, geolocation and similar features disabled), `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`. Provider-injected Cloudflare NEL telemetry must be disabled or documented in the provider configuration; origin code cannot reliably remove headers added downstream.

Railway and `NODE_ENV=production` require an exact HTTPS `ORIGIN` before startup; missing or insecure values fail with a configuration error instead of silently omitting HSTS. This protects new deployments from that configuration mistake but cannot modify an existing deployment or edge settings. Non-production localhost development remains supported.

## Announcements

Announcements are public plaintext retained in announcements.json in the configured data directory until an admin deletes them. Admin authorization is enforced on sends, edits, and deletes; browser controls are only a convenience. Any current admin can manage earlier announcements across sessions. Author name, message ID, original session ID, timestamp, and badge are stored with each post. File writes are serialized and atomically renamed before acknowledgement or broadcast; failed writes leave the visible archive unchanged. The fixed announcement room cannot be removed. Other conversations retain their existing temporary retention and encryption behavior.
